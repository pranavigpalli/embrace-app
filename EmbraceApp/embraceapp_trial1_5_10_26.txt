  Why it can't be a real port:
  - MindRove SDK — only ships Python/C++ bindings. No Swift SDK. You'd have to

  (coremltools), and the CNNLSTMClassifier architecture would need to be
  reproduced in Swift via Core ML or MPS.

  arm's service/characteristic UUIDs and protocol from ble.py would need to be
  ported over.

❯ how was the backend made so that it works with swift?                         

⏺ Nothing was "bridged" — the Python backend can't run on iOS (no PySide6, no
  bleak, no MindRove SDK, no PyTorch). Each of the three backends was
  reimplemented natively in Swift against the same wire protocols.

  1. MindRove EMG → MindRoveClient.swift

  Python (mr.py + openmr/) uses a pure-Python UDP receiver. The actual wire
  protocol is just: the armband broadcasts UDP packets at 192.168.4.1:4210, no
  handshake needed. So I ported the packet parser, not the SDK:

  - Transport: NWListener on UDP port 4210 (Network.framework). Same port the
  Python receiver binds.
  - Packet parsing: rewrote openmr/packets.py in Swift. The 216-byte WUA2 packet
   decodes as 8 × Int32 little-endian at the start, scaled by 0.045 µV/LSB. The
  MES2–MES7 packets use 24-bit big-endian signed values (the _int24_be function
  in packets.py line 47, now parseEMG24 at MindRoveClient.swift:111).
  - Sampling: conn.receiveMessage is push-based — same effect as Python's
  recv-in-a-thread loop.

  The only thing I dropped was scipy-based DSP (openmr/dsp.py), which the app
  doesn't use anyway.

  2. BLE arm → ArmBleController.swift

  Python (ble.py) used the bleak async BLE library. iOS has its own BLE stack,
  CoreBluetooth. Same UUIDs (bf77b1ec-… service, 49b7f353-… characteristic),
  same protocol — one byte written per second representing the gesture index:

  - CBCentralManager replaces BleakScanner + BleakClient.
  - scanForPeripherals(withServices:) replaces the service-UUID-filtered
  discover call.
  - writeValue(_:for:type:.withoutResponse) replaces write_gatt_char.
  - A 1 Hz Timer drains the gesture queue, matching the Python time.sleep(1) in
  the BLE loop.

  It's the same protocol over a different OS-provided BT stack.

  3. PyTorch model → Core ML

  This one isn't reimplementation, it's conversion. PyTorch doesn't run on iOS,
  but Apple's Core ML can execute the same computational graph on the Neural
  Engine / GPU. The pipeline in scripts/convert_model.py:

  1. Reconstruct the CNNLSTMClassifier class in PyTorch (same layer-for-layer
  copy of models.py).
  2. Load bin/best_model_v8.pt weights via model.load_state_dict().
  3. Trace with a dummy (1, 600, 8) input → torch.jit.trace.
  4. Convert with coremltools.convert(..., convert_to="mlprogram", 
  compute_precision=FLOAT16) → produces EmbraceModel.mlpackage.

  Xcode then compiles .mlpackage → .mlmodelc automatically during build. At
  runtime, GesturePredictor.swift loads the model with MLModel(contentsOf:),
  builds an MLMultiArray of shape (1, 600, 8), runs model.prediction(from:), and
   argmaxes the logits — the same np.argmax(self.manager.predict(samples)) from
  models.py:177.

  So the buffering logic from ModelThread.run() (lines 163–178: deque, wait for
  600 samples, stack, predict) became GesturePredictor.feed(): append sample,
  return prediction when buffer hits 600.

  Why this works

  The Python program isn't really "logic on top of MindRove + BLE" — it's a thin
   glue layer over three external protocols:

  ┌───────────────┬────────────────┬─────────────────────────────────────┐
  │     Layer     │     Python     │                Swift                │
  ├───────────────┼────────────────┼─────────────────────────────────────┤
  │ EMG transport │ UDP socket     │ NWListener (UDP)                    │
  ├───────────────┼────────────────┼─────────────────────────────────────┤
  │ EMG parser    │ openmr.packets │ MindRoveClient.parseWUA2/parseEMG24 │
  ├───────────────┼────────────────┼─────────────────────────────────────┤
  │ BLE           │ bleak          │ CoreBluetooth                       │
  ├───────────────┼────────────────┼─────────────────────────────────────┤
  │ ML inference  │ PyTorch        │ Core ML                             │
  ├───────────────┼────────────────┼─────────────────────────────────────┤
  │ UI            │ PySide6/Qt     │ SwiftUI                             │
  └───────────────┴────────────────┴─────────────────────────────────────┘

  Each row swaps the implementation but keeps the protocol identical. The wire
  bytes the iPhone sends and receives are bit-for-bit the same as what app.py
  would send.
